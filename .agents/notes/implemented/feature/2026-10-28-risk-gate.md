# Agent Note: Check relay requests through a staged risk gate

Status: implemented

## Problem

The violation guard (`2026-10-25-violation-guard.md`) acts only after
Anthropic refuses a request. The first violating request of every
conversation still reaches a pool account, and so does a near copy of a
prompt that another customer already had refused. There is no place to stop
known distillation harvests or obviously prohibited requests before they are
billed and forwarded, and nothing shows operators how much traffic each kind
of check stops.

## Decision

- **`service.CheckRiskGate` runs in `controller.Relay` where the violation
  guard ran**, before billing and channel selection, in four stages:
  1. **Distillation** (`distill`): a rule list matched against the system
     prompt and the latest human message.
  2. **Hard regex** (`hard_regex`): a rule list matched against every human
     message. Human text is what the violation guard already extracts: tool
     results and `<system-reminder>` blocks are excluded.
  3. **Refusal cache** (`refusal_cache`): the violation guard's suspensions
     and refused conversations, then a shingle Jaccard comparison of the
     latest human message with the messages Anthropic refused within the
     strike window, from any customer. Messages under 32 characters are not
     compared, and the result is cached per message until the refused set
     changes, because the latest human message repeats on every tool step.
  4. **Decision model** (`decision`): the human messages, latest marked
     `[current ask]`, go to a Jev Decisions endpoint (`POST /v1/systemone`)
     with one `noul` question per line. The highest probability at or above
     the threshold blocks. The address may be Jev itself or the engine, which
     already routes Decisions.
- **The first stage that hits decides.** In `enforce` mode it returns 403
  `risk_gate_blocked`; in `observe` mode it records the hit and the request
  passes without running later stages. Suspensions and refused conversations
  keep following the violation guard's own mode and error codes.
- **A hit can count as a violation.** Each stage except the refusal cache has
  a strike switch. A strike goes through `applyViolationStrike` with category
  `gate:<stage>:<rule>`, so the guard's merge, suspension and ban policy
  applies and the conversation is then held by stage 3. Nothing is struck
  while the guard is off. A strike's excerpt never feeds the similarity set:
  only upstream refusals do.
- **The decision model costs one call per human turn.** Verdicts are cached
  for an hour by the hash of address, model, questions and state. Claude Code
  resends unchanged human messages on every tool step, and parallel requests
  with the same text share one call. A failed call passes the request and is
  recorded as `fail_open` by default; with fail-open off it blocks that
  request without a strike, because a failure is no evidence against the
  customer.
- **Rules are option values, not code.** This repository is public, and a
  published rule list tells an abuser what to avoid. `risk_gate_setting.*`
  accepts legacy "name | regex" lines. A complete vm2api distillation JSON
  object in `distill_rules` selects the structured detector; `hard_regex_rules`
  then uses case-insensitive JavaScript regexes, including lookbehind. Both
  values validate before save, and leaving structured mode requires replacing
  JS-only hard rules first. Saving the first structured policy also validates
  the saved Go-syntax hard rules as JavaScript, which changes their semantics
  and rejects Go-only syntax; clear them before that save. The key ends in `api_key`, so `GET /api/option/`
  does not return it.
- **Two new tables back the console's risk audit.** `risk_gate_events` keeps
  each hit with the latest human message (4 KB) for 30 days, so an operator
  can judge a false positive. `risk_gate_hourly_counts` counts requests in and
  decision calls per hour; counters are buffered for 30 seconds, written by
  increment so two servers during a release add up, and flushed on shutdown.
  `GET /api/user/risk_gate/summary` and `/events` are admin-only and declared
  for personal access tokens as `user:read`.
- **The gate is off by default and starts in observe mode**, so enabling it
  changes nothing for customers until an operator has read its hits.

## Alternatives considered

- **Only convert vm2api's regex strings.** The original implementation did
  not port its rules without commercial permission. After the operator
  confirms authorization, the structured detector follows version 1.4.023,
  revision `06e5a0be1d89cd74e0f60f12f44646179ab1977b`, including client
  exemptions, structure checks, prompt extraction and preprocessing. A
  text-only conversion cannot preserve those context-dependent decisions.
- **A separate service between new-api and the engine.** It would need the
  customer's identity passed along, parse every body a second time and add a
  network hop, and could not stop a request before billing.
- **The engine's request audit.** It sees only new-api's one access key, so it
  cannot strike a customer, and it runs after billing.

## Consequences

- Legacy policies scan Messages and Chat Completions. Structured policies
  also scan Responses and Responses Compaction through the original cached
  JSON body. Multipart/audio requests are not parsed as chat policies. The
  existing refusal-cache, JEV and punishment policies are not migrated.
- The decision model adds up to `decision_timeout_ms` to the first request of
  each human turn while it is on.
- The similarity set is per process and reloads every ten minutes, so a
  refusal recorded by the other server during a release is seen late.
- Up to 30 seconds of counters are lost if the process dies without a
  shutdown.

### Structured detection semantics

`pkg/riskpolicy.Evaluate` preserves distillation order: hard needles,
additional patterns, official/zero exemptions, user-preferred fingerprints,
ordinary needles, then contest structure. Distill-category hard rules remain
controlled by the distillation switch even when the hard-regex switch is off.
GPT requests bypass the deterministic stages unless `openai_platform_enabled`
is true; their distillation checks still stay off. Hard rules retain source
order and scan deduplicated, normalized user history, excluding tool payloads
and closed reminders/environment metadata before source-ordered base64 expansion.

`moejs`, already a direct dependency, supplies JavaScript regex semantics;
Go/regexp2 case folding and character widths are not equivalent. Pooled
runtimes have one owner at a time, retain compiled patterns, and interrupt a
match after 200 ms. A fault in either mode, including a request body that
cannot be read as a JSON object, records `fail_open` under the stage that
failed and lets the later stages run: a gate does not reject a request because
of its own fault, and one slow pattern must not turn large requests into 503s.
A customer who provokes a timeout therefore skips the deterministic stages for
that request, not the refusal cache or decision model. This resource bound
differs from the source's unbounded execution.

An untransformed request is scanned once; vm2api passes the same body as
inbound and transformed, which joins its system prompt twice. Verdicts are
cached for an hour by a hash of both rule sources, the stage switches, the
client and zero-injection flags, the harvest structure result and the texts
the rules read, because Claude Code resends the history on every tool step.
With 18 simple hard rules, an 800 KB request takes 66 ms uncached and 6 ms on
a hit, which is the text extraction and hash. Faults are not cached.

Official-client recognition reads the User-Agent, `metadata.user_id` and the
system prompt, all set by the client, so a non-Claude Code client can copy
them. With `skip_official`, such a client skips fingerprints, ordinary needles
and contest structure; hard needles, patterns and hard rules still apply. Invalid lone-surrogate JSON
strings and evidence truncated within a surrogate pair become U+FFFD in Go;
ordinary valid Unicode and the supplied source policy are covered by comparison.

Optional JSON flags are `zero_inject` (false),
`detect_proxied_official_cc` (true), and `openai_platform_enabled` (false).
Zero injection is an operator-selected context, not inferred from a customer's
prompt. Source `error` metadata is retained and validated, but CoreCode keeps
its existing error envelope, observation and strike policy. The original
license and attribution are retained in `pkg/riskpolicy/LICENSE.vm2api` and
`NOTICE`. Rule bodies remain private operator configuration.

## Verification

- `TestRiskGate` passes on SQLite 3.50.4, MySQL 5.7.44 and PostgreSQL 9.6.24,
  three runs under `-race`. It checks that a distillation hit in the system
  prompt blocks, strikes as `gate:distill:<rule>` and then is held by the
  refusal cache; that tool results never trigger hard regex and observe mode
  only records; that a near copy of an upstream refusal is blocked for
  another customer while the gate's own verdicts and short messages are not
  compared; that the decision model blocks above the threshold with one call
  for two identical requests, fails open, and fails closed without a strike;
  and that the summary counts requests, calls, failures and hits.
- `go test -p 1 ./model/ ./controller/ ./service/` passes 2670 tests against
  the same three databases, including `TestMigrationSchemaStability`.
  `go test ./...` passes on SQLite. `GOWORK=off go build ./...` passes in
  `relaykit`.
- Migration on each of the three databases: the `main` binary created the
  schema, then this binary started twice; every start served `/api/status`
  with no error in its log, and the two tables have the expected columns,
  keys and indexes.
- End to end on SQLite: with a hard regex rule in enforce mode, a matching
  `/v1/messages` request got 403 `risk_gate_blocked` before the price check,
  a clean one passed the gate, and the summary and events endpoints returned
  both requests in and the one hit. An invalid regex was rejected on save,
  and the saved key was absent from `GET /api/option/`.
- Frontend: `bun run typecheck`, `bun run format:check` and `bun run build`
  pass; oxlint reports nothing in the changed files; `vitest run
  src/features/system-settings` passes 230 tests, including the funnel
  arithmetic and the stage filter of the new dashboard.
